# 多媒体朋友圈展示系统 · 小组开发指南

这是本课程大作业的**项目根目录**。第一次参与项目时，从本文件开始阅读，再看 `specs/proposal.md`、`specs/design.md` 和自己负责的任务。M02 动态模块已建立独立工程并完成模块自测；完整系统仍待其他模块与前端接入。

## 项目目的与技术栈

项目要开发一个类似朋友圈的多媒体动态展示系统：用户在小程序中发布文本、图片或视频，给动态添加标签，按日期和标签检索，并对其他人的动态评分、评论；管理员在 Web 后台查询和管理用户及动态。

| 部分 | 采用的技术 |
| --- | --- |
| 用户小程序 | uni-app、Vue 3、TypeScript，构建微信小程序 |
| 管理后台 | Vue 3、TypeScript、Vite、Element Plus |
| 服务端 | Java 21、Spring Boot 3.5、Spring Web、Spring Security、Spring Data JPA、Flyway、Maven |
| 数据库 | MySQL 8.4 LTS |
| 身份认证 | 账号密码登录、BCrypt 密码哈希、JWT 登录令牌 |
| 媒体存储 | 服务端本地文件目录，数据库保存文件元数据 |
| 测试 | JUnit 5、Spring Boot Test；前端使用 Vitest |

加分项统计图采用 Apache ECharts。具体架构和运行约定见 `specs/design.md`。

## 目录和文件分别做什么

| 路径 | 用途 | 什么时候看或修改 |
| --- | --- | --- |
| `README.md` | 给组员看的导航、协作流程和目录说明 | 第一次加入项目时阅读；目录或流程变化时更新 |
| `AGENTS.md` | 给 Codex 等开发助手的项目上下文与工作约定，也可供组员快速查阅 | 使用开发助手前阅读；项目规则变化时同步更新 |
| `specs/proposal.md` | 项目目标、课程必做项、加分项、验收场景 | 开始开发前确认范围；需求变化时先更新 |
| `specs/design.md` | 技术方案、模块边界、页面、权限和数据设计 | 设计和联调时查阅；方案变化时更新 |
| `specs/tasks.md` | 八人总分工、工作量、依赖、里程碑和交付安排 | 阶段交接、依赖变化和验收时更新 |
| `成员任务/` | 八份个人任务文档，各含五阶段清单、测试、素材和工作记录 | 各成员每次工作结束都更新自己的文件 |

| `specs/decisions/` | 记录重要选择及原因，例如技术栈、登录方式、文件存储 | 有不同方案需要取舍时新增记录 |
| `src/miniapp/` | 用户小程序代码 | 开发用户端页面与交互时使用 |
| `src/backend/` | 服务端代码，负责 API、业务规则、权限和数据访问 | 开发服务端功能时使用 |
| `src/admin-web/` | 管理员 Web 后台代码 | 开发用户与内容管理界面时使用 |
| `tests/` | 自动化测试、必要的手工验收记录和演示数据说明 | 完成功能时补测试及验收证据 |
| `deliverables/` | 最终实验报告、四个附件表格和课堂展示 PPT | 整理课程提交物时使用；代码仍放 `src/` |

当前可运行的模块测试见 [M02 动态工程](src/backend/modules/posts/README.md)，结果见 [M02 测试证据](tests/evidence/M02/README.md)。小程序、Web 后台和服务端主工程仍待对应负责人合入；模块测试通过不代表完整系统已经可启动。

## 开发文档怎么用

1. **先定范围**：全组确认 `proposal.md` 的必做功能、加分功能取舍和演示流程。老师原始要求优先于本项目草案。
2. **按方案设计**：在 `design.md` 阅读既定技术栈、认证、媒体存储和业务规则；如需变更，在 `decisions/` 记录原因和影响。
3. **先约定再分头实现**：前后端共同确认 `contracts/api.md` 与 `contracts/data-model.md`。接口路径、字段、权限和错误码要以约定为准。
4. **执行个人任务**：在 `成员任务/` 对应文件填写姓名和日期，按 S1–S5 推进；每阶段测试已完成的内容，每次工作追加记录，有验收证据后才标记完成。
5. **变更同步**：需求变更先改 `proposal.md`，设计变更再改 `design.md`，接口变更改 `contracts/`，最后同步 `tasks.md` 和受影响代码。组员联调前检查文档版本。
6. **按交付物验收**：核心流程能从登录一直演示到管理员管理；测试结论与报告、PPT 中的描述一致。

## 文档状态和协作约定

- **课程要求**：来自老师给出的要求，必须完成；如有新通知，以老师最新版本为准。
- **项目约定**：本项目采用的业务规则、接口和技术栈。修改时按上述流程同步相关文档。
- **成员编号**：M01～M08 对应八份任务。M02（锡汉唐）独立实现与 48 个模块测试已完成，真实联调及同伴验收待进行；其他成员按实际提交更新状态。
- 一项任务由一名负责人维护进度，涉及接口的任务须与调用方共同确认。
- 不把真实密码、密钥或真实用户数据提交到项目；演示数据使用虚构内容。

## 建议的阅读顺序

新组员：`README.md` → `specs/proposal.md` → `specs/design.md` → `specs/tasks.md` → 本人的 `成员任务/` 文档 → 相关 `specs/contracts/`。

开发助手：先读 `AGENTS.md`，再按任务读取相关规格文档。给开发助手下达任务时写明需求编号或任务编号，例如“T05，完成按标签与日期检索，并按现有 API 契约实现”。
