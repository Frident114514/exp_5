# M01 初步压力测试实测记录

日期：2026-11-25（北京时间）。本轮确认：本人信息查询在最高已测 1000 请求/秒的 20 秒档位全部成功；10000 请求批量放行的成功率为 64.74%，未满足容量门禁。没有把 503 或限流拒绝计入成功。

## 环境与方法

AMD Ryzen 9 8945HX，32 个逻辑处理器，约 31.3 GiB 内存；Windows；Java 21.0.8；MySQL 8.4.13；Java 堆上限 2 GB。服务端采用 high-concurrency 虚拟线程 profile，本人查询并发预算 64，Hikari 最大 20，认证 10 请求/秒、突发 20、并行 4。

负载生成器为 .NET 10 异步 HttpClient。k6 下载遇到网络中断，本轮没有使用 k6 执行；仓库仍保留 k6 等价脚本。负载端、应用和数据库同机，结果不是独立生产环境容量。测试在随机端口和独立空库运行，10000 个账号使用同一虚构测试密码对应的 BCrypt 哈希，预先生成各自合法 JWT，避免查询档混入登录计算。每次查询核对返回账号。

持续负载按固定到达率开始任务，每次一个 HTTP 请求，活动请求上限 1000；请求超时 10 秒。瞬时实验准备 N 个任务后统一放行，但客户端和网络调度仍有跨度。所有档位丢弃调度、无效 200 响应及其他异常 HTTP 状态均为 0。

## 结论与下一步

1. 当前 M01 查询路径在已测 1000 QPS 短档表现正常；未探索其持续吞吐上限。
2. 1000 与 10000 请求批量档均有 503，说明当前本人查询预算下尚不能高成功率承载该突发场景。下一步应在独立压测机上保持同一负载和数据口径，对比并发预算、数据库等待及实例数，不能只扩大连接数。
3. 20 秒档位不构成长时间稳定性验收。全系统动态、评分评论、媒体流量尚未接入本次测试，需补混合负载及热点场景。
4. 复现：PowerShell 7 设置 JAVA_HOME 后，执行 tests/performance/run_local_m01.ps1 -MysqlBin <MySQL 8.4 bin目录>。脚本创建隔离实例，结束后停止本次 Java/MySQL 并删除令牌夹具；不会连接正常开发库。
