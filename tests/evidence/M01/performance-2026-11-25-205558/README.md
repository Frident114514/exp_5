# M01 请求观测改造与万人压测端校准

2026-11-25（北京时间）。本轮只改变观测与计量，不改变 64 个本人查询名额、20 个数据库连接、即时 503 和用户状态即时校验。保留现有预编译语句配置；不将本轮与旧客户端的不同数字解释为性能收益。

## 503 对账与时间区间

`reconciliation.json` 对客户端与服务端按试验名称、顺序编号一一匹配，不含账号、密码或令牌：

- 10000 个编号均恰好到达一次；服务端 entered=completed=10000，缺失、重复、状态不一致、超出采集上限均为 0。
- 准入拒绝 7324 + 过滤器数据库异常 0 + 全局数据库异常 0 + 其他已观测 503 为 0 + 未在过滤器观测的 503 为 0 = 客户端 503 总数 7324。
- 获准处理 2676，恰好与成功数相等。服务端过滤器区间最大重叠 93；观测的获准处理区间最大重叠 64。名额释放观测点位于实际 release 之前，微小探针间隙单独保留，不等同于精确 CPU 执行并发。
- 获准请求的数据库查询区间 P95 92.75 ms，包含连接获取、SQL、结果映射；不是纯 SQL 耗时。观测的持有名额区间 P95 104.28 ms。全体请求过滤器 P95 18.38 ms，混有大量快速拒绝，不能当作成功请求延迟。

由此，本轮“大量 503 主要由立即名额拒绝产生”的假设得到直接支持。仍未采集连接获取与 SQL 独立耗时、Hikari 等待分布，不能据此断言数据库没有等待或盲目扩池。下步先区分数据库查询内各阶段，再在负载与探针相同条件下做单变量对照。

## 测量定义及边界

客户端每请求记录单调时钟：开始写、写完、首次观测到响应字节、响应头完成、HTTP 消息体完整、解析完成。以 Content-Length 或 chunked 边界判定完整响应，不再等 socket EOF；响应读取立即进行。原始 `HttpClient` 稳态路径无法观测 socket 写完与首字节，字段填 -1，不伪造计时。失败记录分类、异常类型和套接字错误码，不保存异常消息。

服务端在默认关闭的诊断模式中记录过滤器进入、获准、释放前观测、数据库查询起止、过滤器退出及响应状态。它们是应用区间，不是完整请求头收到至最后响应字节发出的网络区间；两端单调时钟原点不同，不直接相减。每试验最多 60000 个编号、最多 16 个试验，超额显式计数，无逐请求同步文件日志。管理员接口读取快照，非管理员不可读取。

`SERVER_TOMCAT_CONNECTION_TIMEOUT=60s` 在本轮整个 Java 进程内生效，包含预热、建连、业务施压和恢复，不是只在准备阶段生效。默认应用配置仍为 5 s，本轮不能命名为默认 5 s 下的容量成绩。请求总超时改为 15 s 并如实记录；成功请求 SLA 仍为 P95 <1 s，未放宽门禁。

资源采样请求间隔为 100 ms，并区分 preconnect、requests、complete；CIM 和系统调度会使实际间隔更长，以记录时间为准。采样增加 .NET GC 次数和线程池待处理项，仍未证明压测端资源有余量。负载、Java、MySQL 同机，诊断探针本身有开销，本轮不能量化探针对性能的影响或声明稳定优化收益。

## 复现与证据

```powershell
./tests/performance/run_local_m01.ps1 -MysqlBin '<MySQL 8.4 bin目录>' -BurstOnly -Calibrate
./tests/performance/analyze_m01.ps1 -Evidence './tests/evidence/M01/performance-2026-11-25-205558'
```

`calibration.json` 单列接收屏障校准；逐场客户端与服务端 traces 为原始事件，`reconciliation.json` 为编号、503 与区间重叠分析。`resources.json` 记录阶段化采样，`experiment.json` 记录实际配置。服务端诊断模式的 20 项单元与真实 MySQL 回归全部通过，涵盖来源分类、断连后释放、全局数据库异常、采集上限、重复编号、管理员权限及原有账号禁用/tokenVersion 即时失效。
