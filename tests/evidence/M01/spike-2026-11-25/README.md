# M01 万连接突发复验与优化试验

2026-11-25（北京时间）。结论：已经完成 10000 条 TCP 连接预建和 10000 个真实 HTTP 请求的集中放行，当前仍未通过万人请求容量门禁；未证明 10000 个请求同时在服务器执行。扩大处理中名额和短暂等待均未达 SLA，已回退这两项试验改动，保留补丁与证据。最终仅在 high-concurrency profile 启用有界预编译语句缓存，保持 64 个处理中名额和 20 个数据库连接。

## 方法与验收

10,000 个不同的虚构账号、各自合法 JWT，逐次核对响应账号。独立 MySQL 8.4.13、Java 21、high-concurrency profile，数据库池 20。压测端和服务端仍在同一台 Windows 机器。先预建 10000 条 TCP 连接；建连采用最多 128 个并行任务，瞬时拒绝最多重试 4 次。建连重试不属于业务请求重试；放行后每连接恰好一个 GET /api/v1/users/me，不重试失败业务请求。

连接准备阶段将 Tomcat connection-timeout 设为 60 s，防止首批空闲连接在准备完成前被关闭；正式应用配置未改。请求超时 10 s。10000 个任务由同一个门统一放行，立即接收响应，不人为积压响应凑在途数。maxInFlight 从客户端请求方法进入算到完整响应解析结束，包含发送调度与客户端读取耗时；不是服务器执行并发。maxAwaitingResponse 也包含正在写入的请求。firstResponseMs 早于 lastDispatchMs，说明首批完成时末批尚未发完。10000 连接、10000 次请求和10000 同时在途是三个不同指标。

业务门禁保持成功率 >99%、成功请求 P95 <1000 ms、调度丢弃 0；429、503、传输异常和账号错误均不算成功。严格万人同时在途还须有达到 10000 的实际在途证据；本轮未满足。原始 pass 只表示脚本业务门禁，不代替负载达成判定。

## 优化判定

1. 将本人查询处理中名额 64 提高到 256，在统一放行试验中成功数由 3891 降至 2786、成功 P95 由 382.52 ms 升至 847.42 ms；本次未证明收益，因此没有扩大默认名额。单次同机结果存在调度波动，这不是对所有部署环境的普遍结论。
2. 维持 64 个处理中名额，新增最多 10000 个虚拟线程等待、每次最多 750 ms。1000 QPS 预热 20 s 的条件下，成功数 2916→3631，但成功 P95 368.93→2761.34 ms，未达 SLA。短暂等待并未解决本轮端到端突发瓶颈，已回退。实验补丁见 rejected-wait-policy.patch；其当时 8 项并发单元测试通过，但单元测试通过不等于容量通过。
3. 最终保留原先 64 个处理中名额、20 个数据库连接、即时 503 保护以及实时账号状态检查；没有减弱 JWT/密码安全或用缓存掩盖用户禁用生效语义。

4. JFR 诊断共 392 个执行样本；46 个样本的首个相关栈位于 MySQL FullReadInputStream.readFully，42 个栈顶为 GHASH.blockMult；38 个 JavaMonitorEnter 事件中 36 个位于连接关闭时的 SelectorImpl.cancel。采样提示数据库协议/加密、HTTP 处理和连接关闭共同产生开销，没有足够证据认定唯一瓶颈。JFR 附加开销下结果单列，未与普通试验直接计算性能收益；原始 JFR 留在本地，仓库仅保存不含请求数据的 [聚合统计](jfr-summary.json)。

5. 在 high-concurrency profile 设置 cachePrepStmts=true、useServerPrepStmts=true、prepStmtCacheSize=32、prepStmtCacheSqlLimit=1024。按 20 个数据库连接计算，驱动每连接最多缓存 32 条语句，认证查询可复用解析/预编译，不缓存用户状态或响应。依据：[Connector/J 缓存配置](https://dev.mysql.com/doc/connector-j/en/connector-j-connp-props-performance-extensions.html)、[服务端预编译配置](https://dev.mysql.com/doc/connector-j/en/connector-j-connp-props-prepared-statements.html)。16 项真实 MySQL 回归全部通过。相同 1000 QPS 预热 20 s 和统一放行方法下，该轮成功 4520/10000（原配置该轮 2916/10000），成功 P95 398.96 ms，仍未通过 >99% 成功率门禁。这是同机探索性观测，未做重复统计，不能保证普遍的提升倍数。

## 后续可执行的验收步骤

先把压测客户端移到独立机器，使用同一批账号及同一门禁，记录请求实际到达分布、服务端入口活动峰值与客户端资源。在证明负载确实达到万人同时在途后，再比较多个应用实例与入口分流，同时保持数据库总连接预算；并用服务端耗时、GC、连接池等待和 SQL 耗时定位瓶颈。现有单机结果不足以把瓶颈完全归因于数据库、CPU 或网络，不直接承诺横向扩容倍数。
