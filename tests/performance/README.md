## k6 备用脚本

新增 `successful_requests`、`responses_429`、`responses_503`、`transport_errors` 计数和 HTTP 200 的 `successful_request_duration` 时延趋势及门禁；业务账号一致性由 checks 独立核查。

压测对象为独立测试环境中的完整 HTTP 服务和 MySQL 8.4。脚本需要本机已有 k6；没有安装时先准备工具。本脚本不代表系统已通过万人容量验收。

准备 `users.local.json`，每项为 `{"account":"load_001","password":"虚构测试密码","accessToken":"预先登录取得的令牌"}`。使用专用测试账号；令牌有效期为 12 小时。该文件已在本目录忽略规则中。多个账号覆盖不同用户记录，避免把单账号热数据当成全部负载。

PowerShell 示例，从项目根目录运行：

```powershell
$env:M01_USERS_FILE = './users.local.json'
$env:BASE_URL = 'http://127.0.0.1:8080/api/v1'
$env:MODE = 'me'
$env:RATE = '20'
$env:DURATION = '60s'
$env:P95_MS = '1000'
k6 run tests/performance/m01-auth.js
```

`M01_USERS_FILE` 由 k6 的 open 相对脚本目录解析；示例文件放在 `tests/performance/users.local.json`。登录压测改用 `MODE=login`，由低速率开始；登录限流默认 10 请求/秒，超出时 429 是保护行为，但仍计为未满足成功请求容量目标。登录响应包含令牌，不开启 HTTP 调试日志。

`RATE` 表示每秒开始的迭代数，本脚本每次迭代发 1 个 HTTP 请求；`VUS` 默认 50，`MAX_VUS` 默认 200。按 20、50、100、200 RPS 等档位探索本人信息容量，硬件、数据量和业务目标明确后再制定正式阈值；不直接跳到 10000 并发。需要更大负载时确认压测机资源足够，再调整 VU 上限。

默认门禁：请求错误率 <1%、P95 <1 s、业务检查成功率 >99%、`dropped_iterations=0`。这些是起始验收建议，可用 `P95_MS` 调整时延目标。记录每档实际成功 RPS、429/503、P95/P99、CPU、GC、内存、Hikari 活跃/等待连接和 MySQL 慢查询。拒绝请求不能当成功吞吐；快速返回 429 也不能说明业务延迟达标。测试期间不重启或改配置。

## 1 万在线的容量基准

采用 `QPS = 10000 × 活跃比例 × 每人每秒操作次数 × 每次操作平均 HTTP 请求数` 推导目标，再按浏览/写入/登录/媒体比例拆分负载。在线人数不等于同时执行的请求数。活跃比例、操作频率、请求放大系数、峰值系数及机器配置待依据演示或真实业务测量填写，不将示例值当正式目标。

正式验收在推导负载下同时满足约定 SLA、错误率和资源健康范围；先预热，再持续稳定施压。瞬时并发另设实验，观察限流、超时、恢复及数据一致性。M01 脚本先验证登录和携令牌查询两条路径，待其余模块接入后补全混合业务场景。

## 1 万请求同时到达专项

服务端可启用 `high-concurrency` profile；压测客户端设置 `MODE=me`、`BURST_VUS=10000`。此时每个 VU 发 1 个请求，尽可能同时启动；实际到达分布仍取决于压测机与网络，不保证数学意义上的同一瞬间。先以 100、500、1000 个 VU 校验资源和行为，再提高至 10000；压测端也须有足够资源。

本人信息测试预先准备令牌。不要让 1 万个 VU 先同时登录，否则测到的是 BCrypt 与登录限流。专项仍保留 HTTP 200、成功率和时延门禁；429/503 均视为未成功承载。记录成功数、拒绝数、超时数、分位数及整批完成耗时，失败同样保存。若要达到高成功率，需要按实测调整实例数量、入口调度和数据库预算；不能仅提高连接上限便宣称通过。

浏览、写入和媒体仍须在相应模块接入后增加独立与混合场景。M01 的限流并发测试验证资源保护及恢复，不代替整系统压力测试。
