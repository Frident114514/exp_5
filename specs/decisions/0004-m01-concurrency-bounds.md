# M01 并发资源控制

- 日期：2026-11-25
- 状态：已实现 M01 边界；业务基准确定为 1 万在线、部分用户活跃，按推导的峰值 QPS 和 SLA 验收，瞬时并发用于补充极限探测。
- 范围：注册、登录、本人信息、JWT 用户状态查询与服务端资源配置。

BCrypt 保留当前强度。注册和登录共用单实例令牌桶，默认每秒补充 10 个请求名额、突发最多 20；密码接口同时最多处理 4 个请求，超限立即返回 429，不排入应用级等待队列。本人信息接口独立限制为 64 个处理中请求，超过返回 503。过滤器置于 JWT 处理之前；异常、客户端断连和正常完成均释放名额。

JWT 每次仍查询数据库中的角色、账号状态和 tokenVersion，但使用只读 DTO 投影，不读取 password_hash，不缓存认证状态，保留状态变更后的即时拒绝语义。后续其他受保护业务入口须按模块设计各自的并发预算；本人信息名额不等于整个 API 的并发上限。

主工程配置有界 Tomcat 线程池与队列、Hikari 连接池及等待超时、JDBC 建连和读超时，以及 JPA 查询超时提示。JPA 提示不等于整个请求的绝对截止时间。默认参数是单实例的初始压测配置，不能据此宣称通过万人验收。Tomcat 在应用之前拒绝连接时，不能保证返回应用统一 JSON。

限流状态位于进程内。部署 N 个实例时，总允许速率约为 N 倍；正式横向扩容时须在入口协调全局额度。未引入 Redis 或用户状态缓存，避免改变即时失效语义。实例间须共用数据库和 JWT 密钥；媒体共享存储、热点写锁及媒体流式传输由其他模块负责。

容量推导采用 `在线人数 × 活跃比例 × 每人每秒业务操作数 × 每次操作平均 HTTP 请求数`，再按实际突发及业务分布设定峰值。各参数、读写/登录/媒体占比和部署机器资源需随实际场景登记，不能凭在线人数直接指定 10000 QPS。登录峰值单独计算；客户端复用已签发令牌，业务请求不重复执行 BCrypt。媒体字节流另记带宽，不用小 JSON 的 QPS 代替视频承载能力。

可重复的集成验证：`src/backend/scripts/verify_mysql.ps1`。容量压测脚本：`tests/performance/m01-auth.js`。登录与本人信息分开压测，记录 429/503，不能将拒绝请求计为成功吞吐。

补充目标：尽量成功承载 1 万请求同时到达。为此提供可选 `high-concurrency` profile，启用 Java 21 虚拟线程和较高的连接上限，保留数据库、密码计算与本人查询预算。脚本以 `BURST_VUS` 切换一次性并发请求模式。高并发连接、成功业务请求及响应 SLA 分开报告；该 profile 是待测配置，不是已达标结论。
