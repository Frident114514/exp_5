## 01｜多媒体朋友圈展示系统

建议用时：20 秒。

大家好，我们小组拟开发一个由用户小程序和管理员 Web 后台组成的多媒体朋友圈展示系统。本次汇报主要介绍我们对课程需求的分析、初步设计、最终确认的八人分工，以及拟定的开发进度。

依据：小组最终分工表；specs/proposal.md。

## 02｜项目目标

建议用时：30 秒。

我们将系统定位为一个支持多媒体展示与互动的课程项目。用户侧解决内容发布、个人管理和检索交流的问题，管理员侧提供统一管理能力。项目验收将围绕一条完整流程展开：先发布，再由另一位用户检索和互动，最后验证作者管理与后台管理，保证各模块可以协同运行。

依据：specs/proposal.md 第 1、2、4、8 节。

## 03｜需求范围

建议用时：35 秒。

必做功能按照两个终端划分。小程序覆盖账号、发布与本人管理、检索、评分和评论；后台覆盖用户与动态管理。删除用户在实现层采用禁用，删除动态采用逻辑删除。好友、敏感词过滤、视频流处理、大模型与统计图保留为加分候选，是否投入开发取决于核心功能完成后的实际进度。

依据：specs/proposal.md 第 2、3、5 节；最终分工表 A6:A13。

## 04｜业务流程与验收场景

建议用时：35 秒。

核心验收会使用两个普通账号和一个管理员账号。用户甲发布，用户乙检索、浏览并互动，随后用户甲编辑或删除，再由管理员执行管理操作。除了页面能正常操作，还必须检查身份、权限和数据状态。例如非作者不能编辑动态，改密后旧令牌失效，删除后的详情与媒体也应不可读取。

依据：specs/proposal.md 第 8 节；specs/contracts/api.md；data-model.md。

## 05｜总体架构与技术栈

建议用时：40 秒。

架构采用两个前端共用服务端的形式。小程序使用 uni-app、Vue 3 和 TypeScript，后台使用 Vue 3 与 Element Plus。服务端采用 Java 21 和 Spring Boot，按控制器、业务服务、数据访问分层。MySQL 保存业务与媒体元数据，文件放在独立媒体目录。统一接口和角色规则有利于八人并行开发；Flyway 用于同步数据库结构。

依据：specs/design.md 第 1、5、6 节；specs/decisions/0001-tech-stack.md。

## 06｜核心数据模型

建议用时：40 秒。

数据模型以动态为中心。用户可以发布多条动态，一条动态可以包含多个媒体，并通过关联表对应多个标签。评分和评论都关联用户与动态，其中评分通过用户和动态的联合唯一约束实现重复提交时更新原评分。用户和动态都保留状态字段，用于禁用和逻辑删除；管理行为另外记录日志。这里展示的是初步关系设计。

依据：specs/contracts/data-model.md。

## 07｜发布与管理流程设计

建议用时：40 秒。

发布时先上传媒体，服务端验证后返回媒体 ID，再提交文本、标签与媒体 ID。动态服务需要核对上传者与作者身份，完成关联后才能公开访问；超过二十四小时未绑定的媒体将清理。删除与禁用则需要跨模块协调，保证列表、详情和媒体访问一致，禁用用户时还需要撤销令牌并处理其互动数据。

依据：specs/design.md 第 9 节；specs/contracts/api.md；data-model.md。

## 08｜页面与交互方案

建议用时：30 秒。

页面采用围绕任务组织的方式：广场负责发现内容，发布页负责输入与上传，详情页集中展示媒体和互动，后台使用列表完成管理。本页是设计示意，并非系统截图。我们会由小程序基础负责人统一按钮、表单、请求和错误状态，其他页面复用这些约定，重点处理上传失败、空结果以及删除确认等场景。

依据：specs/proposal.md 第 7 节；specs/design.md 第 7、10 节；最终分工表 A10:A13。

## 09｜质量保证与测试计划

建议用时：35 秒。

测试分为模块测试、真实接口联调和完整流程验收三个层次。每位成员测试并修复自己负责的模块，梁国浩负责汇总验收矩阵和测试报告。测试记录需要保留执行人、环境、操作步骤、实际结果和证据，发现缺陷后还要复验。当前这些内容是验收计划，后续只把实际执行过并有证据的结果记为通过。

依据：最终分工表 A6:A13，尤其 A9；tests/README.md。

## 10｜服务端四人分工

建议用时：40 秒。

服务端由四位成员承担。组长侯坚楷负责基础工程、认证与用户管理，并协调进度和接口；锡汉唐负责动态、标签和检索，整理数据库关系图；潘铭伟负责媒体服务和环境复现；梁国浩负责评分评论及测试汇总。各负责人同时承担本模块测试与材料整理，汇总工作不会替代其他成员的实际测试。

依据：小组最终分工表 A6:B9。

## 11｜前端四人分工

建议用时：40 秒。

前端由四位成员分工。李赫卓维护小程序框架、公共请求和账号页面，姚语嫣负责发布、编辑和我的动态，王誉负责广场、检索、详情和互动，并汇总全员 PPT 素材。叶天豪负责管理员 Web 后台、报告排版和交付清单。每位成员都需提供自己的真实素材，并在汇总后核对本人内容。

依据：小组最终分工表 A10:B13。

## 12｜接口对接与协作方式

建议用时：35 秒。

并行开发首先要把接口说清楚。账号服务主要对接账号页与后台，动态服务对接发布、广场和后台，媒体服务对接上传和播放，互动服务对接详情页。每次工作结束都记录修改、测试、问题和下一步，每个阶段至少由一位对接成员复验。用户禁用等跨模块操作由组长统筹，避免各模块分别完成后仍存在状态不一致。

依据：最终分工表中的协作对象及完成条件；specs/contracts/api.md。

## 13｜建议六周进度

建议用时：40 秒。

最终分工表已经确认人员，但还没有填写具体日期，因此这里提出六周安排供小组确定。第一周完成需求、数据与接口约定；第二周跑通账号和工程骨架；第三到第四周并行完成服务与页面，并开始真实联调；第五周集中回归与补齐证据；第六周完成材料、环境复现和演练。模块测试从实现阶段持续开展，报告素材也随个人记录积累。

依据：分工表 A6:A13 的阶段交付；六周安排为本次拟定，尚未确认日历日期。

## 14｜里程碑与风险应对

建议用时：35 秒。

进度不能只看代码提交数量，每个阶段都要有能够验证的产出。第一周看约定是否一致，第二周看最小流程能否跑通，第四周看真实联调，第五周看回归证据，第六周看交付和演示。主要风险是接口变动、媒体环境差异和联调过晚，因此我们会分批对接并预留收尾时间，核心功能未通过时暂缓加分功能。

依据：最终分工表的验收标准；specs/design.md 第 6、10 节；本次建议里程碑。

依据：课程要求；最终分工表 A8、A9、A12、A13；deliverables/README.md。
